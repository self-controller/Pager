## 1. App stack options and trade-offs (which reuses the most of the existing React 19 / Vite / Tailwind reader?)

### Takeaway
Capacitor (wrapping the existing Vite build in WKWebView) reuses nearly 100% of the React reader UI and still allows adding Swift code and native extension targets later; Expo/React Native can reuse React components only through webview-based "DOM components"; a PWA reuses everything but cannot do background downloads, Bonjour discovery, Files-app integration, or reliable "permanent" offline access; native SwiftUI, Flutter, Tauri and Skip reuse little or none of the UI code. The catch for every non-PWA option is that the developer is on Linux (see Section 2).

### Cited Findings

**PWA / Home Screen web app (Safari)**
- In iOS 26/iPadOS 26, every website added to the Home Screen opens as a web app by default (an "Open as Web App" toggle is on by default in the Add to Home Screen sheet); before iOS 26 that required a manifest or meta tag — [heise](https://heise.de/-10749652); [Michael Tsai, Oct 3 2025](https://mjtsai.com/blog/?p=49472).
- Storage policy (Safari 17+): browser apps get an origin quota of up to 60% of total disk and overall quota up to 80%; a Home Screen web app "has the same origin quota and overall quota as when it is opened in a browser app." Eviction is LRU by origin when quota is exceeded, under storage pressure, or after ITP inactivity; default mode is best-effort (evictable) — [WebKit: Updates to Storage Policy](https://webkit.org/blog/14403/updates-to-storage-policy/).
- `navigator.storage.persist()` is granted by heuristics, "like whether the website is opened as a Home Screen Web App" — [WebKit: Updates to Storage Policy](https://webkit.org/blog/14403/updates-to-storage-policy/).
- Safari's 7-day cap on script-writable storage for non-installed sites does not apply to Home Screen web apps (developer forum consensus citing WebKit ITP docs) — [Apple Developer Forums 710157](https://developer.apple.com/forums/thread/710157).
- Home Screen web app data is isolated from Safari (a user signed in in Safari arrives signed out in the installed app); iOS web apps have no Background Sync / periodic background fetch, so any scheduled work must happen server-side and reach the device via push (secondary vendor source) — [MagicBell PWA iOS limitations](https://www.magicbell.com/blog/pwa-ios-limitations-safari-support-complete-guide).
- Web Push for Home Screen web apps arrived in iOS/iPadOS 16.4; it requires the site to be added to the Home Screen with a manifest whose `display` is `standalone` or `fullscreen`, and permission can only be requested in response to direct user interaction; Badging API also supported — [WebKit: Web Push for Web Apps on iOS and iPadOS](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/).
- Declarative Web Push (push without needing a service worker) shipped for Home Screen web apps in iOS/iPadOS 18.4 — [WebKit: Meet Declarative Web Push](https://webkit.org/?p=16535); [WebKit Features in Safari 18.4](https://webkit.org/blog/16574/digital-credentials-api/).
- EU/DMA: Apple initially said it would remove Home Screen web apps in the EU (iOS 17.4 betas, early 2024) but reversed course and continues to offer them, built on WebKit — [512 Pixels: Apple Reverses Course on PWAs in EU](https://512pixels.net/?p=28982). I found no 2026 change to this.

**Capacitor (wrap the existing React/Vite build)**
- Capacitor 8 (Dec 8, 2025) made Swift Package Manager the default for new iOS projects (CocoaPods projects still work) — [Ionic: Announcing Capacitor 8](https://ionic.io/blog/announcing-capacitor-8).
- Capacitor 8.5 (July 31, 2026) is an iOS-only "breaking minor" adopting UIScene, which iOS 27 requires for apps built with the latest SDK; migration is `npm i -D @capacitor/cli@latest` then `npx cap migrate`; apps built with Xcode 26 are unaffected — [Ionic: Capacitor 8.5 released](https://ionic.io/blog/capacitor-8-5-released).
- An Aug 28, 2026 Ionic post forecasts Capacitor 9 for end of November 2026 and notes CocoaPods trunk goes permanently read-only on December 2, 2026 — [Ionic blog, Aug 28 2026](https://ionic.io/blog/?p=6904).
- Capacitor iOS: "iOS 15+ is supported. Xcode 26.0+ is required"; it uses WKWebView; the iOS platform is an Xcode project you open (`ios/App/App.xcworkspace`) and extend with plugins "or custom native code" — [Capacitor iOS docs](https://capacitorjs.com/docs/ios).
- A real Capacitor app added a native iOS Share Extension target in Xcode, shared data with the main app via an App Group, and bridged to JS via files read with the Capacitor Filesystem plugin — [TimeSafari iOS share extension notes](https://gitea.anomalistdesign.com/trent_larson/crowd-funder-for-time-pwa/src/commit/4b118b0b91a66505e02073f3a3a5c49e4fc06adc/doc/ios-share-extension-setup.md).

**React Native / Expo**
- Expo "DOM components": add the `'use dom'` directive to a web React component file and import it into a native screen; it renders in a webview on native (via `@expo/dom-webview` by default on SDK 56+, react-native-webview on earlier SDKs), and Expo positions it for "incremental migration for an entire website to a universal app" per component; props must be serializable — [Expo docs: DOM components](https://docs.expo.dev/guides/dom-components/).
- Expo's native runtime "generally does not support elements like `<div>` or `<img>`" — i.e., the existing Tailwind/HTML components do not run natively without the DOM-component webview — [Expo docs: DOM components](https://docs.expo.dev/guides/dom-components/).
- `expo-apple-targets` (Evan Bacon) can add native Apple extension targets (including a `file-provider` type) to an Expo project via `expo prebuild`; "Most extension types cannot run React Native" — [expo-apple-targets target list](https://www.mintlify.com/EvanBacon/expo-apple-targets/targets/complete-list); [expo-apple-targets GitHub](https://github.com/EvanBacon/expo-apple-targets).

**Tauri 2 mobile**
- Tauri's iOS distribution uses Xcode to archive/distribute; App Store distribution requires the Apple Developer Program — [Tauri v2: App Store distribution](https://v2.tauri.app/fr/distribute/app-store/). Third-party guide: local iOS development needs macOS + Xcode; from Linux, build iOS via GitHub Actions `macos-latest` runners — [Bini.js iOS platform guide](https://bini.js.org/docs/platform-ios).

**Skip (Swift → Android)**
- Skip became free and open source in early 2026: from v1.7 all licensing (keys, EULA, evaluation period) is removed; the core "skipstone" engine is AGPL-3.0; "Skip Fuse" compiles Swift natively for Android, "Skip Lite" transpiles Swift to Kotlin — [Skip: Skip is free](https://skip.tools/blog/skip-is-free); [AlternativeTo, Jan 2026](https://alternativeto.net/news/2026/1/swift-cross-platform-framework-skip-is-now-free-and-open-source-with-licensing-removed); [skiptools GitHub](https://github.com/skiptools).

**App Review constraints that affect "wrapper" stacks**
- Guideline 4.2: apps "should include features, content, and UI that elevate it beyond a repackaged website"; 4.2.2: apps shouldn't primarily be "web clippings, content aggregators, or a collection of links" — [App Store Review Guidelines](https://developer.apple.com/app-store/review/guidelines/).
- Guideline 2.5.2: apps may not "download, install, or execute code which introduces or changes features or functionality of the app" — [App Store Review Guidelines](https://developer.apple.com/app-store/review/guidelines/).

### Inferences
- **Most reuse:** Capacitor wrapping the bundled Vite `dist/` is the closest to "ship the existing reader on iPhone": same React 19 + Tailwind code, same highlight/notes UI, plus native plugins (filesystem, background downloads via a custom Swift plugin, push) and the option to add a File Provider extension target later. Expo DOM components are a second-best route if the developer wants native navigation/shell with the reader view embedded as a webview component.
- **Do not just point the wrapper at the home server's URL.** Loading the UI live from `http://<home-pc>:3006` inside a Capacitor/RN webview risks Guideline 4.2 (repackaged website) and 2.5.2 (downloaded code changes functionality), breaks completely offline, and makes App Review dependent on reaching the server. Bundle the frontend in the app and talk to the server only as an API/content source.
- **PWA is the zero-cost, no-Mac, no-$99 path** and is viable for a personal-use MVP: iOS 26 makes "Add to Home Screen" open as a web app by default, Home Screen apps escape the 7-day ITP deletion and get large quotas, and Web Push works. But it falls short of "permanent access" goals: no background downloads, no Bonjour discovery, no Files-app provider, storage is still best-effort/evictable unless `persist()` is granted, and the PWA's origin is tied to whatever URL serves it (LAN IP vs. Tailscale hostname vs. public domain are different origins with separate storage). It also needs HTTPS for service workers (secure context), which the current plain-HTTP port 3006 server would not provide.
- **SwiftUI native** gives the best platform integration (Readium, File Provider, background URLSession, Bonjour) but discards the React UI; it pairs naturally with xtool on Linux (Section 2). Flutter offers no reuse of React code. Skip only matters if Android is also a goal and still assumes Swift/SwiftUI authorship.
- Tauri 2 mobile reuses the web frontend like Capacitor but has a smaller iOS plugin ecosystem and still needs macOS/Xcode for builds; Capacitor is the more mature choice for this case.

### Gaps
- I found no source documenting iOS 27-specific changes to Home Screen web apps (storage, push, service workers). Wikipedia's iOS 27 article mentions none.
- No official confirmation found on whether Declarative Web Push / Web Push behave identically in the EU in 2026.
- Did not verify Flutter's 2026 iOS tooling status or Tauri 2 mobile plugin maturity for background downloads.
- Did not verify whether Capacitor's iOS WebView origin (custom scheme) counts as a secure context for Web Crypto/service-worker-dependent libraries.

## 2. Building and signing iOS apps from Linux (no Mac)

### Takeaway
In October 2026 there are three workable no-Mac routes: (1) **xtool** builds, signs and installs SwiftPM/SwiftUI apps natively on Linux (very actively maintained, v1.24.0 released Oct 26, 2026, supports app extensions and custom entitlements); (2) **Expo EAS Build** (cloud macOS builders; free tier currently lists 15 iOS builds/month); (3) **macOS CI/cloud Macs** (GitHub Actions macOS runners, Codemagic's 500 free macOS minutes, AWS EC2 Mac with a 24-hour minimum) for Capacitor/Tauri/RN Xcode builds. Signing for real devices or TestFlight needs an Apple account; device builds via EAS require the paid program.

### Cited Findings

**xtool (native Linux)**
- xtool is a "cross-platform Xcode replacement" that builds a SwiftPM package into an iOS app, signs and installs iOS apps, and talks to Apple Developer Services programmatically; runs on Linux, WSL, and macOS; Linux install is via an AppImage from GitHub Releases; commands include `setup`, `auth`, `sdk`, `new`, `dev`, `ds`, `devices`, `install`, `uninstall`, `launch` — [xtool GitHub](https://github.com/xtool-org/xtool); [xtool README](https://cdn.jsdelivr.net/gh/xtool-org/xtool@main/README.md).
- You must supply your own `Xcode.xip`; xtool builds the iOS SDK from it rather than shipping Apple files; licensing concerns were raised and the author told users to read the license agreement — [Swift Forums xtool announcement (May 8, 2025)](https://forums.swift.org/t/xtool-cross-platform-xcode-replacement-build-ios-apps-on-linux-and-more/79803); OSNews noted the tool doesn't address Apple's Xcode licensing terms — [OSNews](https://www.osnews.com/page/45/?not=apple).
- Limitations as of the May 2025 announcement: no Interface Builder (not planned), no asset catalogs (raw images work), Apple-proprietary macros like SwiftData needed rebuilding, only application targets, no integrated LLDB (workaround: pymobiledevice3 + lldb remote), no App Store deployment, no direct .xcodeproj support — [Swift Forums xtool announcement](https://forums.swift.org/t/xtool-cross-platform-xcode-replacement-build-ios-apps-on-linux-and-more/79803).
- Release history since then (from GitHub releases): `xtool dev build --ipa` (1.11.0, May 2025); custom entitlements via `entitlementsPath:` in `xtool.yml` (1.12.0, May 2025); Xcode 26 beta + Swift 6.2 (1.13.0, June 2025); **App Extensions support (1.14.0, July 2025)**; wifi-aware entitlement and Xcode 26.3 fixes (1.18.x, Sept 2026); **Swift 6.4, SwiftUI macros, SwiftBuild-based builds "a lot closer to Xcode", Xcode 27 recommended (1.20.0, Sept 21 2026)**; FoundationModels macros (1.20.1); Apple ID login now presents as a "Pixel 7" device fingerprint to fix auth (1.22.2, Oct 14 2026); Apple ID auth can be used "as opposed to an App Store Connect API key" (1.23.0, Oct 22 2026); Sign in with Apple entitlement and a fix for HTTP 503 errors on Apple ID auth (**1.24.0, Oct 26 2026**) — [xtool releases](https://github.com/xtool-org/xtool/releases).

**Expo EAS Build (cloud)**
- Official pricing page (fetched Oct 2026): Free = up to 15 Android + 15 iOS builds/month, low-priority queue, 45-min build timeout, 1 macOS concurrency; Starter $19/mo + usage ($45 build credit, high priority); Production $199/mo + usage ($225 credit); Enterprise custom; iOS builds cost $2 (medium) / $4 (large) worker beyond credit — [Expo pricing](https://expo.dev/pricing).
- Conflicts: an Expo pricing snapshot elsewhere advertised 30 builds/month and $99 Production; a third-party tracker reports a change from 30 to 15 builds/month dated Aug 28, 2026 — [PricingSaaS: Expo](https://pricingsaas.com/companies/expo); [Expo pricing.md](https://expo.dev/pricing.md). Expo billing docs (modified Sept 7, 2026) say Free gets "a limited quantity of low-priority builds," limits reset monthly, and Free accounts cannot incur overages — [Expo billing plans](https://docs.expo.dev/billing/plans/).
- iOS Simulator builds on EAS are unsigned and need no Apple credentials; physical-device builds need a paid Apple Developer account for signing — [Expo: test iOS app without a Mac](https://expo.dev/articles/testing-and-previewing/test-ios-app-without-mac); [Expo: work without a Mac](https://docs.expo.dev/preview/simulators/how-to/work-without-a-mac/).
- "Expo Simulators" (remote iOS Simulator on an EAS Mac, controlled from a browser) is a limited-access preview for select partners with a waitlist, not included in plans — [Expo: work without a Mac](https://docs.expo.dev/preview/simulators/how-to/work-without-a-mac/).

**macOS CI / cloud Macs**
- GitHub Actions: standard GitHub-hosted runners are free in public repos; GitHub Free personal accounts get 2,000 minutes/month; macOS 3–4 core runners are $0.062/min (SKU `actions_macos`) — [GitHub Docs: Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions); larger M2 Pro runners $0.102/min — [GitHub Docs: runner pricing](https://docs.github.com/en/enterprise-server@3.17/billing/reference/actions-runner-pricing).
- Codemagic (third-party trackers, mid-2026): free tier 500 macOS M2 minutes/month, 1 concurrent build; pay-as-you-go Mac mini M2 $0.095/min, M4 $0.114/min — [CI/CD Calculator: Codemagic](https://cicdcalculator.com/codemagic-pricing); [AgentDeals: Codemagic](https://agentdeals.dev/vendor/codemagic).
- AWS EC2 Mac: Dedicated Hosts billed per second with a **24-hour minimum allocation** (tied to Apple's macOS license); M2 (mac2-m2.metal, 24 GiB) and newer M4/M4 Pro instances exist; Savings Plans up to 44% off — [AWS EC2 Mac FAQ](https://aws.amazon.com/ec2/instance-types/mac/faqs/).
- Running macOS on non-Apple hardware (Hackintosh/VM) violates Apple's license terms — [OpenReplay: build iOS app without Mac](https://blog.openreplay.com/build-ios-app-without-mac/).

**Toolchain requirement for App Store uploads**
- Since April 28, 2026, apps uploaded to App Store Connect must be built with Xcode 26 or later using the iOS 26 SDK — [Apple: Upcoming requirements](https://developer.apple.com/news/upcoming-requirements/); older-SDK builds fail with ITMS-90725 — [GitLab runner issue 39211](https://gitlab.com/gitlab-org/gitlab-runner/-/issues/39211).

### Inferences
- **If the app is SwiftUI-native:** xtool is now a credible daily driver on Fedora — build, sign (free Apple ID or paid), install to an iPhone over USB, add a File Provider or other extension target (supported since 1.14.0), set entitlements. For TestFlight/App Store upload, either confirm xtool's current upload support or produce the `.ipa` with `xtool dev build --ipa` and upload via a separate tool or a one-off macOS CI job.
- **If the app is Capacitor/Tauri/bare RN:** builds require Xcode, so use GitHub Actions macOS runners (free if the repo is public) or Codemagic's free 500 minutes. A personal app with infrequent releases fits comfortably in those free tiers. AWS EC2 Mac's 24-hour minimum makes it the most expensive for occasional builds.
- **If the app is Expo:** EAS is the smoothest Linux path (managed credentials, store submission), and 15 free iOS builds/month is enough for a hobby project; but device testing still needs the paid $99 program, and the live iOS Simulator is waitlisted. Day-to-day iteration on Linux would rely on a development build on a physical iPhone plus Metro over the network.
- Expect Apple-ID-based auth in xtool to break occasionally (three auth-related fixes in October 2026 alone); App Store Connect API key auth (paid account) is the more robust path.

## 3. Distribution options and App Review considerations

### Takeaway
Free Apple ID provisioning (7-day profiles, 3 apps per device, 10 App IDs per 7 days) works for a personal app but needs weekly re-signing (xtool, AltStore, SideStore). The $99/yr Apple Developer Program gives year-long signing, TestFlight (90-day builds, up to 10,000 external testers) and App Store submission. EU Web Distribution is effectively closed to individuals (organization-only eligibility criteria), and App Review for a "connect to your own server" app hinges on Guideline 2.1: reviewers must be given a reachable demo server or a full demo mode.

### Cited Findings

**Free vs paid Apple accounts**
- Free account (Personal Team): "You can register up to 10 App IDs, which expire after 7 days. You can register up to 3 devices, which expire after 7 days. You can install up to 3 apps per device"; device provisioning profiles expire 7 days from issuance — [Apple: Compare memberships](https://developer.apple.com/support/compare-memberships/).
- Apple DTS tip: reuse the same bundle ID to avoid exhausting the 10-App-ID limit ("You may create up to 10 App IDs every 7 days") — [Apple Developer Forums 724896](https://developer.apple.com/forums/thread/724896); [mybyways blog](https://mybyways.com/blog/new-limitations-imposed-on-free-apple-developer-account).
- Apple's capability table distinguishes ADP, ADEP and the no-cost "Apple Developer" tier (Apple Account holders who agreed to the Developer Agreement, who "can't distribute apps"); "FileProvider Testing Mode" is marked development-only — [Apple: Supported capabilities (iOS)](https://developer.apple.com/help/account/reference/supported-capabilities-ios).
- A paid $99/year membership removes the 3-app cap and gives one-year signing (secondary sources) — [DEV Community: how iOS sideloading works](https://dev.to/1_king_0b1e1f8bfe6d1/how-ios-sideloading-actually-works-in-2025-dev-certs-altstore-and-the-eu-exception-1m2h); [Tenorshare](https://www.tenorshare.com/ios-app/how-to-sideload-more-than-3-apps-altstore.html).

**TestFlight**
- Builds are testable for up to 90 days; up to 10,000 external testers and up to 100 internal testers; external builds may need Beta App Review (first build of a version) — [App Store Connect Help: TestFlight overview](https://developer.apple.com/help/app-store-connect/test-a-beta-version/testflight-overview).

**Sideloading for personal use (AltStore / SideStore)**
- With a free Apple ID: apps expire after 7 days and only 3 sideloaded apps may be active (helper apps count); AltStore can refresh in the background but the computer running AltServer must be on the same Wi-Fi about weekly; SideStore refreshes on-device via a local VPN and needs a computer only for initial setup (secondary sources; no official 2026 confirmation found) — [XDA: sideload with AltStore](https://www.xda-developers.com/how-to-sideload-apps-on-iphone/); [DEV Community](https://dev.to/1_king_0b1e1f8bfe6d1/how-ios-sideloading-actually-works-in-2025-dev-certs-altstore-and-the-eu-exception-1m2h); [Tenorshare](https://www.tenorshare.com/ios-app/how-to-sideload-more-than-3-apps-altstore.html).

**EU (DMA)**
- Apple's new EU terms (announced Aug 2026, effective Oct 1, 2026): the per-install Core Technology Fee is replaced by a 5% Core Technology Commission on digital transactions in apps distributed outside the App Store; App Store rates are 26% (IAP), 20% (alt payments), 15% (link-out); "Apple will continue to require every alternatively distributed app to go through Notarization" — [Michael Tsai, Aug 18 2026](https://mjtsai.com/blog/2026/08/18/new-eu-app-store-terms-to-comply-with-dma/).
- Web Distribution (install from your own website, iOS 17.5+): eligibility requires the "organization" to meet one criterion — fee-waiver nonprofit/education/government, a low-risk D&B rating, stock-exchange listing, listed VC funding, a USD 1M stand-by letter of credit, a recent clean financial audit, or 2+ continuous years in good standing plus an app with >1M first annual installs worldwide; the Alternative Terms Addendum is superseded by Attachment 14 of the DPLA effective Oct 1, 2026; apps must be notarized and installed only from a registered domain — [Apple: Web Distribution in the EU](https://developer.apple.com/support/web-distribution-eu/).

**App Review for apps that connect to a user's own server**
- 2.1: "include demo account info (and turn on your back-end service!) if your app includes a login. If you are unable to provide a demo account due to legal or security obligations, you may include a built-in demo mode in lieu of a demo account with prior approval by Apple"; "Enable backend services so that they're live and accessible during review" — [App Store Review Guidelines](https://developer.apple.com/app-store/review/guidelines/).
- 4.2.3(i): "Your app should work on its own without requiring installation of another app to function" — [App Store Review Guidelines](https://developer.apple.com/app-store/review/guidelines/).
- 4.2.7 (remote desktop clients that mirror specific software): must connect only to a user-owned host on the local LAN, software fully executed on the host, account creation initiated from the host; "Thin clients for cloud-based apps are not appropriate for the App Store" — [App Store Review Guidelines](https://developer.apple.com/app-store/review/guidelines/).
- 2.5.4: background services only for intended purposes ("VoIP, audio playback, location, task completion, local notifications, etc.") — [App Store Review Guidelines](https://developer.apple.com/app-store/review/guidelines/).
- Real cases: an app working only with a user's local Pi-hole was rejected under 2.1 because no public endpoint/credentials could be provided — [Apple Developer Forums 815919](https://developer.apple.com/forums/thread/815919); a developer was told a temporary review endpoint was acceptable but had to keep it running and was still repeatedly rejected — [Apple Developer Forums 841526](https://developer.apple.com/forums/thread/841526); a LAN-app developer was asked to provide a way to review "without downloading other software" — [Apple Developer Forums 828302](https://developer.apple.com/forums/thread/828302).
- Over 40% of unresolved review issues relate to 2.1 App Completeness (non-working demo accounts, backend down during review) — [Expo: App Store rejection reasons](https://expo.dev/articles/shipping-to-the-app-stores/app-store-rejection-reasons).
- A tracker reports an Oct 16, 2026 guidelines revision (submission checklist reorganization, regulatory documentation, AI content apps); it does not mention self-hosted server apps — [ConductAtlas diff](https://conductatlas.com/diff/apple/apple-app-store-review-guidelines/3543/7653/).

### Inferences
- **Personal-use path with zero spend:** build with xtool on Fedora using a free Apple ID and re-install every 7 days (or use SideStore/AltStore). Workable but annoying, and capabilities that typically need a paid team (push, App Groups for extensions, Network Extension) are likely unavailable or limited — see Gaps.
- **Recommended for "permanent" access:** the $99/yr program — one-year provisioning profiles on your own devices, or TestFlight with 90-day builds (re-upload roughly quarterly) — avoids App Store review entirely while still giving installs that don't break weekly.
- **If going to the App Store:** run a public, always-on demo instance of the Pager server (e.g., a small VPS or a tunnel to a demo library with public-domain books) plus a "demo pairing code" in the review notes, or ship a built-in demo mode. Don't require the Tailscale app for the core experience (4.2.3); position the app like Plex/Infuse-style "connect to your server" apps rather than a remote-desktop mirror (4.2.7 doesn't fit a content reader). Bundle UI code rather than loading it from the server (2.5.2).
- EU alternative distribution offers nothing to an individual hobby developer in 2026 (organization-only eligibility, notarization still required).

### Gaps
- Apple's capability table lost its checkmarks in scraping, so I could not confirm exactly which capabilities (Push Notifications, App Groups, Network Extensions, iCloud) are unavailable to free accounts in 2026.
- No official AltStore/SideStore 2026 documentation of current limits was retrievable; numbers come from secondary guides.
- I did not find official Apple statements or rejection histories for Jellyfin/Swiftfin, Plex, Infuse or Immich; precedent that "own-server" media apps are allowed is widely assumed but not sourced here.
- Did not confirm the Apple Developer Program price on an Apple page (secondary sources say $99/yr).
- Did not research AltStore PAL / EU alternative marketplace terms for individual developers in detail.

## 4. Background execution limits and what "permanent access" can mean

### Takeaway
An iOS app cannot hold the live HTTP event stream open while backgrounded; it gets opportunistic, system-scheduled windows (BGAppRefreshTask ~30 s; BGProcessingTask deferred, e.g., overnight on charge), silent pushes that are rate-limited (~3/hour, device-wide budgets), and out-of-process background URLSession transfers that are the right tool for downloading book files. iOS 26's BGContinuedProcessingTask only extends *user-initiated* foreground work (e.g., "Download my whole library") with a Live Activity. "Permanent access" should therefore mean durable pairing credentials + local copies of books + sync-on-open, not a persistent connection.

### Cited Findings
- `beginBackgroundTask` grants "a limited amount of time" after backgrounding to finish critical work; long transfers should use URLSession — [Apple: Choosing Background Strategies](https://developer.apple.com/tutorials/data/documentation/backgroundtasks/choosing-background-strategies-for-your-app.md).
- BGAppRefreshTask: "The system decides the best time to launch your background task, and provides your app up to 30 seconds of background runtime" — [Apple: Choosing Background Strategies](https://developer.apple.com/tutorials/data/documentation/backgroundtasks/choosing-background-strategies-for-your-app.md).
- BGProcessingTask is for deferrable heavy work "such as overnight when the device charges"; the system decides when — [Apple: Choosing Background Strategies](https://developer.apple.com/tutorials/data/documentation/backgroundtasks/choosing-background-strategies-for-your-app.md).
- Background (silent) pushes: `content-available: 1` without alert/sound/badge, `apns-priority: 5`, `apns-push-type: background`; app gets up to 30 seconds; "If you send background pushes more frequently than three times per hour, the system imposes rate limitations" — [Apple: Choosing Background Strategies](https://developer.apple.com/tutorials/data/documentation/backgroundtasks/choosing-background-strategies-for-your-app.md).
- Silent-push throttling uses device-wide budgets shared with other apps; throttling is disabled when a debugger is attached (misleading in testing); delivery may stop if the user hasn't launched the app for a while; force-quit apps aren't woken — [Apple Developer Forums 660149](https://developer.apple.com/forums/thread/660149); [Apple Developer Forums 757094](https://developer.apple.com/forums/thread/757094).
- Notification Service Extension can run briefly on receipt of a visible push to modify content — [Apple: Choosing Background Strategies](https://developer.apple.com/tutorials/data/documentation/backgroundtasks/choosing-background-strategies-for-your-app.md).
- Background URLSession: downloads run out-of-process and continue while the app is suspended; if the system terminates the app, it relaunches it and calls `handleEventsForBackgroundURLSession`; recreate the session with the same identifier at launch; the downloaded temp file is valid only until `didFinishDownloadingTo` returns; a user force-quit cancels downloads and prevents relaunch; `isDiscretionary` lets the system defer to good power/network conditions — [Apple: Downloading files in the background](https://developer.apple.com/documentation/foundation/downloading-files-in-the-background.md); [Apple: AVAssetDownloadURLSession](https://developer.apple.com/documentation/avfoundation/avassetdownloadurlsession.md); [Apple Energy Guide: Defer Networking](https://developer.apple.com/library/archive/documentation/Performance/Conceptual/EnergyGuide-iOS/DeferNetworking.html).
- BGContinuedProcessingTask (iOS/iPadOS 26.0+): "A task that starts in the foreground and can continue running in the background as needed"; progress shown in a Live Activity the user can cancel; the system can terminate it under resource constraints and prioritizes terminating tasks with little progress; must report progress via `ProgressReporting` — [Apple: BGContinuedProcessingTask](https://developer.apple.com/tutorials/data/documentation/backgroundtasks/bgcontinuedprocessingtask.md); WWDC25 session 227 — [WWDC25: Finish tasks in the background](https://developer.apple.com/videos/play/wwdc2025/227/).
- BGContinuedProcessingTask is not intended for automatic sync/maintenance (user must initiate); registered when the user starts the action; submission strategy "fail" (default) or "queue" — [DEV Community WWDC25 write-up](https://dev.to/arshtechpro/wwdc-2025-ios-26-background-apis-explained-bgcontinuedprocessingtask-changes-everything-9b5); [Apple Developer Forums 797538](https://developer.apple.com/forums/thread/797538). Early reports of the launch handler not firing on iOS 26.0 (DTS could not reproduce) — [Apple Developer Forums 801126](https://developer.apple.com/forums/thread/801126).
- Local network in background: if the app is backgrounded and its Local Network privilege is still undetermined, local network operations are denied silently without prompting — [Apple TN3179](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy).
- Guideline 2.5.4 limits background modes to intended purposes (VoIP, audio, location, task completion, local notifications) — [App Store Review Guidelines](https://developer.apple.com/app-store/review/guidelines/).

### Inferences
- **Event stream:** keep the server's HTTP streaming only while foregrounded; on resume, do a delta sync (cursor/"changes since") of progress, highlights and notes. Treat the stream as a foreground-only accelerator.
- **Book files:** enqueue background URLSession downloads (per-book or per-shelf) so large EPUB/PDF transfers survive suspension; offer a user-initiated "Download library" that can use BGContinuedProcessingTask on iOS 26+ for visible progress.
- **Server-initiated sync:** the Linux server could send APNs background pushes (with an Apple-issued key) when new books/highlights appear, but at most ~2–3/hour and with no delivery guarantee; a visible push ("New book added") is more reliable. BGAppRefreshTask adds opportunistic polling but its timing is system-controlled.
- **Ensure Local Network permission is granted in the foreground (e.g., during pairing)**, otherwise background refreshes on home Wi-Fi will silently fail.
- **PWA comparison:** a PWA gets none of these (no background fetch/sync, no background downloads), only Web Push.

### Gaps
- No source found for iOS 27 changes to BackgroundTasks or BGContinuedProcessingTask.
- No authoritative numbers for how often BGAppRefreshTask actually fires in practice.
- Did not confirm whether Capacitor or Expo have maintained plugins exposing background URLSession downloads and BGTaskScheduler in 2026 (likely requires a small custom Swift plugin).

## 5. Files app integration (File Provider extension)

### Takeaway
A File Provider extension (`NSFileProviderReplicatedExtension`) can expose the remote computer's book folder inside the Files app, but it is a substantial native-Swift project with iOS-specific lifecycle limits and debugging pain; it can be bolted onto Capacitor (Xcode target) or Expo (via expo-apple-targets) but must be written in Swift, and it can be built on Linux with xtool (app extensions supported since 1.14.0).

### Cited Findings
- On iOS, the File Provider extension only runs while it has pending completion handlers, and those have timeouts, so an "upload later in background while holding completion handlers" design is not possible on iOS; Apple advises against manually setting `isUploaded` — [Apple Developer Forums 836161](https://developer.apple.com/forums/thread/836161).
- Partial content fetching (`NSFileProviderPartialContentFetching`) is macOS-only with no iOS alternative — [Apple Developer Forums 776780](https://developer.apple.com/forums/thread/776780).
- Replicated File Provider content fails to display on Shared iPad setups (FB16587660) — [Apple Developer Forums 776521](https://developer.apple.com/forums/thread/776521).
- A developer with a ~4 TB backing store saw `fileproviderd` heavily loaded doing sqlite work; Apple suggested a logging profile for diagnosis — [Apple Developer Forums 842476](https://developer.apple.com/forums/thread/842476).
- A developer building an SSH/SFTP client backend via a replicated File Provider on iOS hit an unrecognized-selector crash at extension start — [Apple Developer Forums 710116](https://developer.apple.com/forums/thread/710116).
- Apple's capability list includes "FileProvider Testing Mode" (development only) — [Apple: Supported capabilities (iOS)](https://developer.apple.com/help/account/reference/supported-capabilities-ios).
- expo-apple-targets supports a `file-provider` target type; target sources live outside `/ios` and are wired in at `expo prebuild`; requires Expo SDK 53+, Xcode 16+, CocoaPods 1.16.2+; "Most extension types cannot run React Native"; an older README called it highly experimental and not part of the official Expo workflow — [expo-apple-targets complete list](https://www.mintlify.com/EvanBacon/expo-apple-targets/targets/complete-list); [expo-apple-targets installation](https://www.mintlify.com/EvanBacon/expo-apple-targets/installation); [@bacons/apple-targets README](https://unpkg.com/@bacons/apple-targets@3.0.2/README.md).
- Capacitor apps can add native extension targets in Xcode and share data with the main app via an App Group (share-extension example) — [TimeSafari notes](https://gitea.anomalistdesign.com/trent_larson/crowd-funder-for-time-pwa/src/commit/4b118b0b91a66505e02073f3a3a5c49e4fc06adc/doc/ios-share-extension-setup.md).
- App extensions generally share the container app's Local Network privilege; extension types assumed to run in the background are denied local network access while the privilege is undetermined; put `NSLocalNetworkUsageDescription`/`NSBonjourServices` in the app's Info.plist, not the extension's — [Apple TN3179](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy).
- xtool added App Extensions support in 1.14.0 (July 2025) — [xtool releases](https://github.com/xtool-org/xtool/releases).

### Inferences
- A File Provider is a "phase 2" feature. For an MVP, a simpler approach is to download books into the app's own container and render them in-app; the File Provider adds value mainly if the user wants to open books in other apps (Apple Books, PDF Expert) or browse the remote folder in Files.
- Because the Pager server already exposes an HTTP API, a replicated File Provider could map server book IDs to `NSFileProviderItem`s and download on demand; uploads (if ever needed) must complete within the completion-handler window.
- Reaching the home PC from the extension over LAN requires the main app to have obtained Local Network permission first; over Tailscale (VPN interface) the local network gate doesn't apply (Section 6).

### Gaps
- Found no 2025–2026 blog post-mortem quantifying the effort of an iOS File Provider (Nextcloud/Synology/Working Copy engineering write-ups not located).
- Did not verify whether free (Personal Team) accounts can sign a File Provider extension + App Group.
- Did not verify the simpler alternative of exposing the app's Documents folder in Files via `UIFileSharingEnabled` / `LSSupportsOpeningDocumentsInPlace`.

## 6. Networking on iOS: Local Network privacy, Bonjour, ATS, and VPN (Tailscale/WireGuard)

### Takeaway
Pairing over LAN needs the Local Network permission prompt (`NSLocalNetworkUsageDescription`, plus `NSBonjourServices` for Bonjour discovery); multicast/broadcast discovery needs a special entitlement, so Bonjour is preferred. ATS blocks plain HTTP and, since iOS 17, raw IP addresses by default, so the app must either declare `NSAllowsLocalNetworking`/IP exceptions or the server should move to HTTPS. Remote access via a VPN (Tailscale) is outside the local-network gate, but iOS allows only one packet-tunnel VPN at a time.

### Cited Findings
**Local Network privacy (Apple TN3179, revised 2026-10-06)**
- "A local network is an IP network associated with a broadcast-capable network interface. Such interfaces include Wi-Fi and Ethernet, but not cellular (WWAN) or VPN"; all multicast addresses and 255.255.255.255 count as local — [Apple TN3179](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy).
- Requires local network access: outgoing TCP connections, UDP unicast/multicast/broadcast sends, connecting a UDP socket, receiving multicast/broadcast; not required: listening for/accepting incoming TCP, receiving UDP unicast. Checks apply to all APIs (Network framework, BSD sockets, URLSession) — [Apple TN3179](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy).
- Resolving `.local` names requires local network access; resolving non-local names via the system resolver does not; all Bonjour register/browse/resolve operations require it and service types must be listed in `NSBonjourServices` — [Apple TN3179](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy).
- **Traffic originating from WKWebView, SFSafariViewController and Safari doesn't require local network access** — [Apple TN3179](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy).
- Multicast/broadcast send/receive on iOS requires the `com.apple.developer.networking.multicast` entitlement; so do browsing arbitrary Bonjour service types or all advertised types — [Apple TN3179](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy).
- There is no API to query or explicitly trigger the permission (FB8711182); trick: connect a UDP socket to a link-local address. With `NWConnection`, denial appears as `.waiting` with `unsatisfiedReason == .localNetworkDenied`; `NWBrowser` reports `kDNSServiceErr_PolicyDenied` (-65570); use `waitsForConnectivity` because the first operation may be denied before the user answers — [Apple TN3179](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy).
- Packet tunnel / app proxy / DNS proxy extensions have local network access regardless of the container app's privilege; simulator doesn't support local network privacy (test on device); an iOS 18 state-sync bug was fixed in 18.6 — [Apple TN3179](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy).

**App Transport Security**
- ATS requires HTTPS for URL Loading System (URLSession) connections, with extra TLS checks; exceptions: `NSAllowsArbitraryLoadsInWebContent` (web views), `NSExceptionDomains`, `NSAllowsLocalNetworking`, `NSAllowsArbitraryLoads`; pinning via `NSPinnedDomains` — [Apple: NSAppTransportSecurity](https://developer.apple.com/tutorials/data/documentation/bundleresources/information-property-list/nsapptransportsecurity.md).
- `NSAllowsLocalNetworking` covers "unqualified domains, `.local` domains, and IP addresses"; "In iOS 17, iPadOS 17, and macOS 14, ATS no longer allows connections to IP addresses by default. Add individual IP addresses and classless inter-domain routing (CIDR) ranges in the NSExceptionDomains dictionary"; Apple suggests setting `NSAllowsLocalNetworking` as a declaration of intent — [Apple: NSAllowsLocalNetworking](https://developer.apple.com/tutorials/data/documentation/bundleresources/information-property-list/nsapptransportsecurity/nsallowslocalnetworking.md).

**VPN / NEPacketTunnelProvider / Tailscale**
- Apple DTS: configurations created with `NETunnelProviderManager` are "enterprise" VPNs and "Only one enterprise VPN configuration can be enabled on the system at a time. If you start NEPacketTunnelProvider A and then start NEPacketTunnelProvider B, then NEPacketTunnelProvider A will stop"; a Personal VPN (`NEVPNManager`) can coexist but the enterprise VPN wins route conflicts — [Apple Developer Forums 675507](https://developer.apple.com/forums/thread/675507); [Apple Developer Forums 17019](https://developer.apple.com/forums/thread/17019).
- Tailscale puts the iPhone and home machine on one private network so the phone can reach the home computer over cellular "as if it were on the same local network" — [AppleInsider, June 30 2026](https://appleinsider.com/articles/26/06/30/how-to-use-tailscale-to-remotely-connect-to-your-mac-from-anywhere).
- Tailscale's iOS app supports VPN On Demand (e.g., connect when leaving home Wi-Fi) — [Tailscale docs: VPN On Demand](https://tailscale.com/docs/features/client/ios-vpn-on-demand.md).
- Channels DVR shipped a TestFlight build with Tailscale embedded in its own app so users don't need the separate Tailscale VPN app — [Channels community thread](https://community.getchannels.com/t/new-dvr-server-tailscale-integration-for-easier-away-from-home-access-experimental/33392?page=4).
- A 2022 user report described heavy battery drain from the Tailscale iPhone app (older data point) — [dbushell.com, 2022](https://dbushell.com/2022/08/18/tailscale/).

### Inferences
- **Pairing on LAN:** have the Linux server advertise a Bonjour service (e.g., `_reader._tcp` via Avahi on Fedora) and browse with `NWBrowser`; list it in `NSBonjourServices`. This avoids the multicast entitlement. Pairing code/computer ID can be carried in the TXT record or exchanged after connecting.
- **Capacitor-specific nuance:** requests made by `fetch()` inside the WKWebView are exempt from the Local Network prompt (TN3179), but if the app uses native HTTP (e.g., CapacitorHttp/URLSession) or Bonjour, the prompt and ATS rules apply. Either way, a plain `http://192.168.x.x:3006` endpoint needs ATS exceptions (`NSAllowsLocalNetworking` or IP/CIDR in `NSExceptionDomains`); web-content loads may need `NSAllowsArbitraryLoadsInWebContent`.
- **Remote access:** three realistic patterns — (a) require the user to run the Tailscale app (simple, but occupies the single VPN slot and conflicts with work VPNs/SideStore's local VPN; also the 4.2.3 "works on its own" risk for App Store); (b) embed a tunnel (Tailscale/WireGuard via your own `NEPacketTunnelProvider`, as Channels did) — still subject to the one-VPN limit and requires the Network Extension entitlement; (c) expose the server through an HTTPS reverse tunnel/relay with a public hostname so the app uses ordinary URLSession with valid TLS (no VPN, ATS-compliant, background URLSession-friendly). Pattern (c) also solves the App Review demo-server problem.
- Because VPN interfaces are not "local network" per TN3179, connecting to a Tailscale 100.x address should not trigger the Local Network prompt; whether ATS's `NSAllowsLocalNetworking` covers non-LAN IPs like 100.x is not stated — using MagicDNS/HTTPS hostnames avoids the question.

### Gaps
- Did not confirm whether the Network Extension (packet tunnel) entitlement is available to free accounts, or current Tailscale embedding licensing/SDK (tsnet/libtailscale on iOS).
- Did not find current (2026) Tailscale iOS battery measurements.
- `NSAllowsLocalNetworking` documentation does not clarify whether it exempts all IP literals or only local ones (e.g., Tailscale CGNAT 100.64.0.0/10).
- No iOS 27-specific changes to Local Network privacy or ATS found (TN3179's 2026 revisions were macOS-related).

## 7. Rendering books on iOS and offline storage

### Takeaway
Three rendering routes exist: Readium Swift Toolkit (native, EPUB + PDF, actively released through 3.11 in 2026; wrapped for RN by react-native-readium), a WKWebView/JS engine (foliate-js or epub.js — natural fit for Capacitor/Expo DOM components and the existing HTML reader), or rendering the server's existing HTML in WKWebView. Downloaded books should live in Application Support (excluded from backup), not Caches, which the OS may purge.

### Cited Findings
- Readium Swift Toolkit release cadence: 3.5.0 (late 2025, EPUB layout/legibility, TTS utilities), 3.6.0 (fixed-layout refinements), 3.7.0 (Feb 6, 2026, comics/large-document performance), 3.8.0 (LCP security, fixed-layout EPUB), 3.9.0 ("major performance gains for PDF", EPUB/PDF navigator refinements, Playground app), 3.11.0 (audio session control, LCP robustness across reinstalls, navigator fixes) — [Readium blog (Swift tag)](https://blog.readium.org/tag/swift/); [Readium blog](https://blog.readium.org); [What's New in Readium Mobile Q4 2025](https://blog.readium.org/whats-new-in-readium-mobile-q4-2025/).
- Swift Package Index logs (July 19, 2026) show failed builds of Readium 3.11.0 under some Xcode/Swift configurations, including Swift 6 data-race errors (automated logs, cause unclear) — [Swift Package Index build log](https://swiftpackageindex.com/builds/C800DC5B-2BE6-462C-9A71-D9F92F6A6D2F).
- react-native-readium wraps Readium for React Native: renders a book view, tracks location, exposes TOC; iOS 13+; EPUB 2/3; no DRM — [react-native-readium (npm)](https://npmjs.com/package/react-native-readium).
- foliate-js: pure-JS, dependency-free e-book library supporting EPUB, MOBI, KF8/AZW3, FB2, CBZ and experimental PDF; "far from complete or stable" though near feature parity with Epub.js; fixed-layout renderer unfinished; IDPF font deobfuscation uses Web Crypto (secure contexts only) — [foliate-js GitHub](https://github.com/johnfactotum/foliate-js).
- epubjs-rn uses EPUB.js to render EPUBs in React Native on iOS/Android (webview approach precedent) — [epubjs-rn GitHub](https://github.com/anwersolangi/epubjs-rn).
- Storage: Library/Caches can be deleted by the system when space is low (not while the app runs) and is never backed up; Apple guidance is to store support files in Application Support and set the do-not-back-up attribute (applying it to a parent directory suffices) — [Apple Developer Forums 107071](https://developer.apple.com/forums/thread/107071); a forum post quotes Apple docs saying "do not back up" data stays on device even in low-storage situations — [Apple Developer Forums 657953](https://developer.apple.com/forums/thread/657953). Third-party guidance: tmp purged anytime, Caches under pressure, Documents/Application Support not purged; check `volumeAvailableCapacityForImportantUsage` — [Axiom storage reference](https://playbooks.com/skills/charleswiltgen/axiom/axiom-storage-management-ref); [Tessl file-storage patterns](https://tessl.io/registry/dpearson2699/swift-ios-skills/3.9.0/files/skills/ios-networking/references/file-storage-patterns.md).
- Background URLSession downloads land in a temporary file that must be moved to a permanent location before the delegate method returns — [Apple: Downloading files in the background](https://developer.apple.com/documentation/foundation/downloading-files-in-the-background.md).
- PWA alternative: Home Screen web app storage is best-effort and evictable unless persistent mode is granted — [WebKit: Updates to Storage Policy](https://webkit.org/blog/14403/updates-to-storage-policy/).

### Inferences
- **Capacitor path:** keep the existing React reader and its HTML rendering; for EPUB, add foliate-js (or epub.js) in the same WKWebView; save downloaded files via the Capacitor Filesystem plugin (or a custom Swift plugin using background URLSession) into Application Support / Library with backup exclusion; store highlights/notes/progress in SQLite on device and sync to the server's SQLite.
- **Native path:** Readium Swift Toolkit gives the most polished EPUB + PDF navigator (decorations API for highlights, TTS) but means rebuilding the highlight/notes UI in SwiftUI; it's a SwiftPM package, so it should be buildable with xtool (unverified).
- If the server already converts books to Substack-style HTML, the simplest offline model is to download that rendered HTML (plus images) per book and display it in WKWebView — the same code path as the web app — rather than parsing EPUB on device.
- Use the server's book ID/hash as the canonical key so on-device copies, highlights (CFI or text-range anchors) and server data stay consistent across devices.

- No Apple primary doc fetched for `isExcludedFromBackup`/purge semantics; findings rely on forum quotes and third-party references.
- Did not verify foliate-js activity level in 2026 or Readium's TypeScript/web toolkit as an option inside a webview.
